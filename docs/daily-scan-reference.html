Technical reference

The daily scan, step by step

Which website the data is taken from, when the scheduled job runs, exactly what we ask Apify for, and every field that comes back. All examples are real, captured from a live run on 7 September 2026.

01Where the data comes from

We scrape one website: Kayak.com. Every one of the 1,047 offers currently in the database came from there, collected by the Apify actor solidcode/kayak-scraper.

A second actor, scrapeunblocker/skyscanner-car-hire-scraper, is configured against Skyscanner but has never run. It only activates if the Kayak actor fails twice on the same search, which has not yet happened.

Kayak is a comparison site, so one scrape reaches the whole market

This is why scraping a single site is worth the money. Kayak does not own any cars. It aggregates offers from booking sites and from the rental companies directly, and all of that arrives in our results.

This distinction matters when the question is “which sites are we scraping?”. Technically and legally the answer is one site. Commercially, we can see almost the whole US rental market through it, including the suppliers that run the monthly programmes we care about.

Booking.com is already reaching us secondhand

Thirty-seven offers in the last scan arrived through Booking.com, which draws on the same inventory pool as the official Booking.com cars API named in the feasibility study as the ideal long-term source. We are getting that data indirectly through a scraper today, where an approved affiliate account would supply it directly, reliably and within terms.

What scraping Kayak means

Kayak's terms of use do not permit automated access. The Apify actor is operated by a third party who breaches those terms; we are the beneficiary. The realistic consequence is that the actor stops working one day, not legal action, but it is not a clean position and it is why the system was built so the data source can be replaced without touching anything else.

02When it runs

The schedule is set by one line in backend/.env. It is currently: 

# minute hour day month weekday
SCAN_CRON=0 6 * * *   → 06:00 every day, server local time

Leave the value empty to disable scheduling entirely. The scanner can still be run by hand at any time.

The clock only ticks while the API is running

The scheduler lives inside the API process. If that process is not running at 06:00, the scan does not happen and nothing is queued for later. For unattended daily operation the process needs a supervisor, such as a Windows scheduled task or a service wrapper. This is not set up yet.

If a previous scan is somehow still running when the clock strikes, the new one is skipped rather than started alongside it, and a warning is logged. Two scans can never overlap.

What happens on one tick

  1. 00:00

    Build the job list

    Active locations are multiplied by pickup dates and durations. Ten locations at three pickup dates gives 30 jobs. Nothing is fetched yet, so this step is free.

  2. 00:01

    Search, five jobs at a time

    Each job triggers two Apify runs, one for vans and one for SUVs. Failures retry twice with a growing delay, and a circuit breaker halts a provider after five consecutive failures.

  3. ~01:05 per job

    Convert every offer

    Vehicle class, monthly rate and deal fingerprint are computed. Excluded suppliers are dropped here.

  4. then

    Store everything

    Every surviving offer is written to PostgreSQL along with the untouched original payload.

  5. then

    Compare with yesterday

    Each deal is matched to the previous run by fingerprint and marked new, cheaper, dearer or gone.

  6. finish

    Write and send the report

    HTML and CSV land in backend/reports/. Email and Slack go out if configured. The dashboard updates on its next load.

03What we ask Apify for

Each job sends two requests to the actor solidcode/kayak-scraper, one per vehicle class. This is the exact input for a van search at Atlanta: 

{
  "pickupLocation": "ATL",
  "pickupDate":     "2026-09-10",
  "returnDate":     "2026-10-10",   // exactly 30 days later
  "pickupTime":     "10:00",
  "returnTime":     "10:00",
  "driverAge":      30,
  "sortBy":         "cheapest",
  "carType":        ["VAN"],       // second request sends ["SUV"]
  "currency":       "USD",
  "maxResults":     80             // SUV requests use 220
}

No drop-off location is sent, which is what makes it a same-location return. Every value here comes from backend/config/scanner.yaml, so changing what the scanner looks for needs no code change.

Why two requests instead of one

Kayak sorts the whole result set by price. Asking for vans and SUVs together meant the cheapest rows were all small SUVs, and the vans were never reached. Splitting the request gives each class its own cheapest-first list. The SUV budget is larger because Kayak's SUV category runs from compact to full-size and the large ones sit deep in the list.

A correction to an earlier note

An earlier summary said Kayak reported this Odyssey as a 12-seat vehicle. That was wrong. Kayak reports 8 seats. The figure 12 came from our own fallback, which filled in a typical seat count for the class whenever the supplier gave none, and it was being used because the seat field was being read from the wrong place in the payload.

That is now fixed, along with two related bugs found in the same review: the ACRISS code and the fuel policy were also being read from the wrong keys, so both were being discarded. Six tests built from this exact payload now guard the mapping. The corrected values apply to future scans; rows already stored keep what they captured at the time.

Still verify seats before booking

Eight seats is what Kayak reports, and the vehicle is labelled a passenger van, but a Honda Odyssey is a seven or eight seat minivan rather than a true 12-passenger van. Any candidate for the 12-passenger requirement must be confirmed on the supplier's own site.

06What each scan costs

Apify charges per row returned, at roughly $1.55 per thousand. There is no charge for compute time, so a slow search costs nothing extra.

  • One van search: up to 80 rows, about $0.12
  • One SUV search: up to 220 rows, about $0.34
  • One job (one location, one pickup date): about $0.47
  • A full daily scan of 10 locations across 3 pickup dates: about $14

Each individual actor run is hard-capped at $0.50 in configuration, so a runaway search cannot drain the account. Today's seven scans of a single location used $1.74 of the $5.00 free credit.
