01What was asked

The brief was to stop manually checking hundreds of US rental locations every day. The system should search nationwide for long-term rentals of minivans, 12-passenger vans and large SUVs, returning the vehicle to the same location, target roughly $1,100 per month, run itself daily, and produce a report showing the cheapest options with vehicle type, rental company, pickup location, dates, total price, monthly average and a booking link, highlighting new deals and price changes.

One question came before any development: does the Skyscanner API actually allow this? That gate is answered in section 2, and the answer changed the shape of the project.

02The feasibility answer

The original plan, to run daily nationwide scans through the official Skyscanner Car Hire API, is not viable. This rests on three things Skyscanner publishes, not on opinion.

  • Access is gated. The Car Hire API is granted only to established businesses with more than 100,000 monthly visitors. Individuals, low-traffic sites and pre-product start-ups are refused.
  • Automated calls are forbidden. Live Pricing may only be called in response to a real user's search. Skyscanner expects 5–20% of searches to end in a booking click. A background scanner produces roughly zero, and access would be revoked.
  • Rate limits. The default is 15 search creations per minute. Hundreds of locations across multiple dates needs thousands of searches a day, which requires a negotiated limit that in turn requires the first point.

A fourth detail matters for any server-side scanner: around half of Skyscanner's quotes come from suppliers that require the end user's IP address. A server has none, so coverage would be roughly halved even with access granted.

A second finding reshaped the search itself. A single 330-day reservation is not something retail booking engines will quote. Long-term rental is sold as monthly programmes: Enterprise Month-or-More from about 28 days, Avis Flex from 60, Hertz Multi-Month from 63, and Hertz's ordinary booking flow caps out near 60 days.

What we built instead

The search unit is a 30-day rental and the system reports an effective monthly rate. Each result carries a note naming the supplier's long-term programme and the day count it starts at, so a human can confirm the extension. The data source is Kayak, reached through a third-party Apify actor, sitting behind an adapter so it can be swapped for an official partner API later without touching anything else.

03What exists now

Two applications, both running against a local PostgreSQL database on this machine. Neither needs a login, because the system is single-user and read-only once a scan has finished.

Backend
NestJS 12 on Node 22, TypeScript throughout. One codebase with three entry points: a command-line worker, a read-only REST API, and a daily scheduler.
Database
PostgreSQL 18, accessed through Drizzle ORM with versioned migrations. Six tables.
Frontend
React 19 with Vite, a results page modelled on flight-comparison sites, plus scan history and per-deal price history.
Data source
Apify actor solidcode/kayak-scraper as primary, with a Skyscanner-based actor from a different author configured as automatic fallback.
Quality
63 automated tests across 10 files. Type checking, linting and production builds all pass clean on both applications.

The pipeline runs in one direction, once per day. Nothing outside the provider folder knows that Apify or Kayak exist, which is what makes the data source replaceable.

04How the important parts work

Deciding what counts as a minivan

Rental listings do not reliably say "12-passenger van". The system classifies each vehicle using the industry ACRISS code when the supplier provides one, where the second letter marks the body type, and otherwise falls back to seat counts and an explicit list of model-name patterns held in configuration. It never simply searches for the word "van", which would match a Vantage sedan.

Every classification records why it fired, so a wrong result can be traced to the exact rule rather than guessed at. Anything that fails all the rules is kept and marked as other, never silently discarded.

Recognising the same deal tomorrow

A deal's identity is a fingerprint built from pickup location, supplier, vehicle identity, pickup date and duration. It deliberately excludes which website sells the booking, so the same Enterprise minivan offered through two booking sites counts once. Without a stable fingerprint, every deal would look new every morning and the report would be noise.

A price move is only reported when it exceeds 3% or $20, whichever is larger. That threshold keeps ordinary daily jitter out of the report.

The monthly rate

Total price divided by rental days, times 30, calculated once in whole cents when the quote is first stored and never recalculated afterwards. Prices are carried as exact decimal strings from the source to the screen, so no rounding drift can creep in between the report and the dashboard.

Knowing when the scanner is broken

A scan that returns nothing but reports no errors is the dangerous failure, because it looks like a quiet market. The system compares each run's quote count against the median of recent runs and raises a warning in the report when it falls by more than half, and treats zero results with zero errors as a bug signal in its own right.

05What the live data showed

Seven real scans ran today against Atlanta Hartsfield-Jackson, for 30-day rentals picked up three to four weeks out. The first useful run exposed a problem that took three iterations to fix, and the fix produced the most important commercial finding of the day.

The search was looking in the wrong place

The first run returned 135 quotes, of which only six qualified, and every one of those was a Turo listing. Turo is peer-to-peer, is an explicit non-goal in the brief, and has no monthly programme to extend into. An uncapped diagnostic search then returned 425 offers across 11 suppliers, including Enterprise, Hertz, Avis, Budget, Dollar and Thrifty.

A correction worth stating plainly

The earlier conclusion that the major rental companies were missing from the data was wrong. They were present the whole time, hidden behind a row limit. Kayak sorts the entire result set cheapest first, so a combined van-and-SUV request spent its whole budget on cheap compact SUVs and never reached the vans.

The $1,100 target is not met at Atlanta

The cheapest qualifying vehicle is $1,178 per month, and the cheapest minivan from a supplier with a monthly programme is $1,493, roughly 36% above target. The only options below $1,100 were Turo listings, which the brief excludes and which cannot be extended into a long-term programme. Either the target needs revisiting, or many more locations must be scanned to find genuine outliers.

Do not trust the seat counts

Kayak labels that Honda Odyssey as a 12-seat passenger van. A real Odyssey seats seven or eight. Seat counts from this source are not reliable for the 12-passenger requirement, and any candidate must be checked on the supplier's own site before booking.

07What it costs to run

The data source charges per result row, at roughly $1.55 per thousand. Today's seven scans of a single location consumed $1.74 of the $5.00 free credit on the organisation account, leaving $3.26.

With the corrected search shape, one location on one pickup date fetches about 300 rows across two searches, costing roughly $0.47. That number drives everything about coverage.

Daily cost at the current row budgets. The original plan assumed $35–60 per month, which the measured rate does not support at wide coverage.

Nationwide daily coverage at full depth is not affordable on this data source. The realistic shapes are a smaller set of high-value locations, fewer pickup dates, or a cheaper official partner API if the client qualifies for one.

08Decisions needed

These are blocking or budget questions that engineering cannot answer alone.

  • Is the $1,100 target still right? Nothing at Atlanta meets it. The target may hold at other locations, but that costs money to discover.
  • Is a 30-day booking with a programme note an acceptable substitute for a 330-day search? This was asked at the planning stage and has never been answered. Everything downstream assumes yes.
  • Has anyone confirmed an actual extension? No human has yet checked with Enterprise or Avis that a 30-day booking really extends toward eleven months at a sensible rate. Until someone does, the premise is untested.
  • How many locations, and what daily budget? See the cost table. This is a straight trade between coverage and spend.
  • Does the client own a business that qualifies for an official affiliate API? Booking.com's cars API would be cheaper, contractually clean and more reliable than scraping.
  • Where should the daily report go? Email and Slack delivery are built but need a mail server or webhook address.

09Running it

PostgreSQL must be running locally and an Apify token must be present in backend/.env. First-time setup creates the database and applies migrations. 

# one time
psql -U postgres -c "CREATE DATABASE car_rental"
cd backend && npm install && npm run db:migrate

# see what a scan would do, free
npm run scan -- plan

# a real scan, limited to two searches
npm run scan -- run --limit 2

# regenerate a report, or compare two runs
npm run scan -- report --run-id 7
npm run scan -- diff 6 7

The API and the dashboard run as two processes. The dashboard reads only from the API and shows an empty state with instructions until a scan has completed. 

cd backend && npm run start:dev   # API on port 3000
cd web && npm run dev             # dashboard on port 5173

All tuning lives in backend/config/scanner.yaml: which locations to scan, how many pickup dates, the price thresholds, the vehicle classification rules, the supplier exclusions and the row budget per vehicle class. Changing what the scanner looks for does not require touching code.
